# 1.7.0 Rust CI cost baseline

This report records the current Rust workflow without changing its matrix,
timeout, checkout depth, or test selection. It is a timing baseline, not a
performance-improvement claim.

## Contract under measurement

The authoritative workflow is
[`rust-test.yml`](https://github.com/eunsoogi/codexy/blob/21f23b1d4a22cc4dc6c09ee92fb3d9f932cfcfc9/.github/workflows/rust-test.yml)
at main head `21f23b1d4a22cc4dc6c09ee92fb3d9f932cfcfc9`:

- 13 Ubuntu and 13 Windows jobs, 26 jobs total.
- `timeout-minutes: 5` for both OS groups.
- `fetch-depth: 0` is unchanged.
- The critical path is the first job start through the last job finish. Gaps
  between staggered jobs remain in that interval.
- Queue time before workflow execution is reported separately from the critical
  path.

## Collection format

Use [`scripts/summarize_test_costs.py`](../../scripts/summarize_test_costs.py)
with one JSON run manifest or an object containing a `runs` list. A run holds
the authenticated job payload plus the following fields:

```json
{
  "run_id": 33948118933,
  "head_sha": "21f23b1d4a22cc4dc6c09ee92fb3d9f932cfcfc9",
  "expected_job_count": 26,
  "condition": "cold",
  "profile_kind": "profiled",
  "created_at": "2026-09-05T05:47:27Z",
  "run_started_at": "2026-09-05T05:47:27Z",
  "jobs": []
}
```

For a profiled job, attach the paths captured from the existing Rust support
contract without adding instrumentation:

```json
"metrics": {
  "profile": "captured-profile.metrics",
  "command_dir": "captured-command-metrics"
}
```

`profile` is the file named by `CODEXY_PROFILE_METRICS` (or the Windows
equivalent). `command_dir` contains the `command-*.metrics` files named by
`CODEXY_PROFILE_COMMAND_METRICS_DIR`. The parser sums `fixture-materialization`
file/byte fields and the `command-wait` sample count.

The opt-in workflow artifacts also contain `measurement.txt`, which records the
frozen head, cold/warm condition, repeat identity, profiling flag, cache
identity, observed cache state, and shard index. The artifact name repeats those
labels so an authenticated artifact listing can be joined to the run and job
payload without treating a missing metric file as zero.

Collect raw run and job data with authenticated reads, then combine the jobs
under the run metadata before invoking the script:

```sh
gh api repos/eunsoogi/codexy/actions/runs/<run-id> > run.json
gh api 'repos/eunsoogi/codexy/actions/runs/<run-id>/jobs?per_page=100' > jobs.json
jq --slurpfile jobs jobs.json '. + {jobs: $jobs[0].jobs}' run.json \
  | python3 scripts/summarize_test_costs.py -
```

Each job result includes job name, OS, head, runner seconds, and checkout,
install, compile, link, and test step seconds. The run result includes the sum
of runner seconds, overlap-aware critical path, queue seconds, fixture totals,
command count, observation cost, and explicit null resource fields. Steps that
combine compilation/linking with `cargo test` remain attributed to the test
command; compile and link are `unmeasured` unless the input supplies explicit
stage labels.

## Smallest executable collection path

The shipped `pull_request` and `push` paths remain uncached and do not set the
profiling variables. The same 26-shard workflow now has an opt-in
`workflow_dispatch` path with these required controls: `head_sha`, `condition`
(`cold` or `warm`), `repeat_id`, `profiling`, and `cache_identity`.

Manual jobs verify the checked-out commit equals `head_sha`. Each job clears and
recreates a stable runner-temp Cargo/Rustup/target location. Cold jobs never
restore a cache. Warm jobs restore the exact key composed of OS, frozen head,
cache identity, and shard index; they fail unless the restore reports a hit. The
same cache identity must be reused for the cold seed and its warm repeats, and a
new identity must be chosen for a new measurement series. Manual jobs upload
only the bounded `metrics` directory: the existing profile file and
command-metrics directory when profiling is enabled, plus `measurement.txt`. A
warm miss records `cache_state=warm-miss` and is rejected rather than counted as
a warm sample; the bounded diagnostic marker is still uploaded when possible. No
raw logs or payloads are stored in the artifact.

This consumer retains the existing 26 targets, target arguments,
`fetch-depth: 0`, permissions, and unconditional five-minute job limits. The
artifact/run metadata and authenticated job timestamps can therefore be joined
into the existing summarizer manifest while keeping queue time separate from the
critical path. Profiling and uninstrumented runs use separate dispatches; the
artifact labels prevent warm experimental data from being presented as the
normal uncached baseline.

The opt-in Ubuntu path intentionally gives Rustup a fresh home, so its cold
condition includes toolchain installation. That setup cost is experimental
measurement overhead and must remain separate from the current hosted-runner
baseline; warm runs restore the same Rustup path. Job step timings and the
observation cost are retained separately.

The controlled collection cannot start from the current draft until this
workflow definition is available on `main` (or an authenticated dispatch
explicitly selects a ref where GitHub exposes this workflow). The parent must
use that authenticated dispatch surface and record its run URLs; this report
does not use a direct GitHub CLI write workaround. Once available, collect three
cold and three warm observations for one frozen head on each OS, and run the
profiling observations as a separate labeled set.

## Required repeated matrix

The required collection is three cold and three warm runs for the same head on
each OS, with profiling and uninstrumented runs separated and observation cost
recorded. That six-sample-per-OS set is not present in the authenticated history
captured above: the available samples are one unprofiled run per two different
heads, and neither has a controlled cold/warm label. The missing repeat set is
an explicit follow-up, not evidence of savings or of a safe matrix reduction.
